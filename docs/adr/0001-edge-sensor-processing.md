# ADR-0001 センサー送信とエッジ側判定の分離

## Status

Accepted (2026-10-28)。Issue #15 の計画と追加回答をユーザが承認した。
2026-10-29: 初期設定・管理の方式は [ADR-0002](0002-customer-device-pairing.md) で更新した。
センサー処理、Wi-Fi / HTTPS の通常通信、保存、Jev 判定の責務は維持する。

## Context

既存構成は、マイコンで姿勢を推定し、画像を Jev に直接送っていた。
深度の時系列を保存し、複数のセンサー情報から判断する要件が加わった。
マイコンではセンサーデータを永続保存しない。

## Decision

マイコンは既存 ESP-DL 顔検知と VL53L5CX の測距を担当する。
同じリポジトリの `edge/` に Rust アプリを配置する。
エッジ側で認証、SQLite 保存、品質判定、Jev 呼出しを行う。
通信は HTTPS とデバイス別キーで保護する。
管理画面も HTTPS と管理者認証で保護する。
判定は 3 分周期で直近 3 分を使用する。
保存は最大 6 時間、全体 100MB とする。

## Alternatives

### Option A: マイコンで Jev 通信を継続

- 既存の通信実装を維持できる。
- 時系列の永続保存と複数デバイスの管理を満たさない。

### Option B: プロジェクトごとに別リポジトリへ分割

- 公開周期と権限を独立させられる。
- 試作段階で送受信契約を同時更新する負担が増える。

## Rationale

実行環境ごとにビルドを分離し、通信契約は同じ変更で管理する。
数値処理と障害時の動作をコードで決め、意味の判断だけを Jev に委ねる。

## Consequences

### Positive

- マイコンの責務と資格情報を限定できる。
- データ不足を外部 API の呼出し前に検出できる。
- 観測と判定期間を記録して評価できる。

### Negative

- エッジの常時稼働と証明書・キーの管理が必要になる。商品向けでは製造側とアプリが担い、お客様の手作業にはしない。
- 旧ストリーム API と旧判定設定の互換性を失う。
- 数値センサーからの姿勢識別能力は実測で確認する必要がある。
