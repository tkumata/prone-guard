# ADR-0002 お客様だけで完結する機器登録

## Status

Designed (2026-10-29)。お客様だけでの接続完結とセキュリティの両立はユーザ指定の必須要件。
再設計と関連文書の修正を実施した。新方式の実装・依存追加・実機検証は未実施。
ADR-0001 のセンサー・保存・判定の分離を維持し、初期登録と管理の方式を本決定で置き換える。

## Context

試作は、作業者が CA と秘密鍵を作り、固定 IP、eFuse、USB 平文 JSON、ブラウザの CA 登録を扱う。
手順のスクリプト化だけでは、開発者なしの導入、登録先の認証、更新・交換・失効を満たさない。
USB の物理接続も、相手の正当性や所有者の権限の証明にはならない。

## Decision

初期登録と復旧は、USB、機器の物理操作、機器固有の登録コードを組み合わせる。
登録セッションには ESP-IDF の Security 2 (SRP6a / AES-GCM) を使う。
通常通信は既存の Wi-Fi STA、HTTPS、機器別 Bearer token を維持する。
エッジアプリが機器別の資格情報とエッジ専用 CA・証明書を管理する。
証明書の信頼はアプリと機器内に限定し、お客様に OS の CA 登録を要求しない。
設定画面をエッジへ集約し、固定 IP・鍵・URL の手入力を不要にする。
詳細な登録状態、更新・復旧手順、受入条件は [接続設計](../current/CONNECTION.md) を正本とする。

## Alternatives

| 方式 | 判断 |
| --- | --- |
| 現行スクリプトと手動証明書設定 | 不採用。開発知識を要求し、認証された登録・失効の仕組みも不足する |
| USB 接続だけで無認証設定 | 不採用。機器の偽装や、接続しただけでの設定上書きを防げない |
| BLE または設定用 Wi-Fi AP | 初期版では不採用。エッジ側の無線機能・ネットワーク切替を追加で要求する |
| 登録専用クラウド | 不採用。今回の登録要件はローカルで満たせ、アカウントとサービス運用を追加する必要がない |
| 通常通信も USB に変更 | 不採用。既存の無線設置と複数ベッドの構成を維持する |

## Consequences

製造時の秘密管理、出荷時の保護検査、配布パッケージ、エッジのローカル設定画面が必要になる。
USB 登録は標準 console の流用だけでは完結せず、既存 USB I/O への transport 接続が必要になる。
CA 変更やエッジ紛失時は、お客様が機器を USB で再接続する。
登録コードと本体の保管、エッジ OS の保護もセキュリティの前提になる。
新方式の受入条件を満たすまで、現行の試作を商品向け接続として扱わない。
