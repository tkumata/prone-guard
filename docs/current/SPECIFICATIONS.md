# センサー送信・エッジ判定の仕様

観測の送受信、OLED 表示、管理 API、保存と判定の契約を定義する。
登録・管理・復旧の詳細は [接続設計](CONNECTION.md)、実装・検証状態は [実装計画](../plans/active/2026-10-28-issue-15-edge-sensors.md) に従う。

## 1. センサー観測 JSONL

マイコンは HTTPS POST `/v1/measurements` に 1 行を送る。
Content-Type は `application/x-ndjson` とし、末尾に改行を付ける。
本文の最大サイズは 16KiB とする。
完全な例は [共通検証例](../../tests/fixtures/measurement.jsonl) を参照する。
検証例は C の実際のシリアライザから生成している。

| フィールド | 型と意味 |
| --- | --- |
| `boot_id` | 起動ごとの 128bit 乱数を 32 桁の 16 進文字列にする |
| `sequence` | 非負の符号付き 64bit 整数。取得周期ごとに増加 |
| `bed_id` | 1〜64 bytes、英数字・`-_.` |
| `timestamp` | 観測の UTC Unix 秒 |
| `camera.status` | `ok` または `error` |
| `camera.timestamp` | 顔検知を完了した UTC Unix 秒 |
| `camera.face_detected` | 0 または 1 |
| `camera.face_area_px2` | 320×240 でクリップした顔矩形の幅×高さ |
| `depth.status` | `ok` または `error` |
| `depth.timestamp` | 測距結果を取得した UTC Unix 秒 |
| `depth.distance` | 符号付き 16bit 整数の 8×8 配列、mm |
| `depth.target_status` | 符号なし 8bit 整数の 8×8 配列 |
| `depth.unit` | `mm` |
| `depth.resolution` | `[8,8]` |

正常な顔未検知は `face_detected:0`、面積 `0.00` とする。
顔検知成立時の面積は 0 より大きく、76800 以下とする。
面積は数値とし、マイコンは小数点第 2 位まで出力する。
取得エラーでは該当センサーの時刻と観測値を `null` にする。
深度のエラー時も `unit` と `resolution` は維持する。
`target_status` は ULD の値を変換せず送信する。
status `5` の距離は 0〜4000mm として検証する。
その他の status の距離は、正常な距離へ置き換えない。
マップの配列方向は ULD の順序を維持する。

観測とセンサーの時刻差は 1 秒以内とする。
未来方向にエッジ時計を 5 秒超える観測は拒否する。
到着が遅い観測は保存できるが、品質条件を満たさなければ判定に使わない。
同じベッド・起動 ID・番号の同じ観測は、再保存せず成功を返す。
同じ識別子で内容が異なる観測は `409` とする。

## 2. エッジ側の HTTP API

全てのエンドポイントを TLS で提供する。

### POST /v1/measurements

`Authorization: Bearer <64 桁のデバイスキー>` を要求する。
エッジ側はキー文字列の SHA-256 と、設定済みの hash を比較する。
ベッド ID は認証済みキーの許可ベッドと一致しなければならない。
商品向けでは、アプリが登録時にキーを発行し、登録状態と有効な世代も毎要求で確認する。
準備中・失効済みのキーは、既存の TLS 接続上でも観測保存に使用できない。

| 応答 | 意味 |
| --- | --- |
| `204` | DB 保存成功、または同じ観測を保存済み |
| `400` | 不正 JSONL、型、配列、値、観測時刻 |
| `401` | キーなし、または不正なキー |
| `403` | 許可外のベッド ID |
| `409` | 起動 ID と番号が同じで観測内容が異なる |
| `413` | 本文が 16KiB 超過 |
| `415` | Content-Type が不正 |
| `503` | 保存失敗 |

### POST /v1/pairing/check

登録準備中の機器が、新しい資格情報による Wi-Fi / TLS 接続を確認するためだけに使用する。
新しい CA と登録ホスト名の検証後に、新しい Bearer token を提示する。
機器 ID、エッジ ID、登録世代、取引 ID が準備中の登録と一致する場合だけ `204` を返す。
本文は JSON、最大 2048 bytes とする。認証不正は `401`、状態・取引の不一致は `409`、本文不正は `400` とする。
観測の保存、登録の確定、管理操作は行わない。確認結果をエッジ側の登録状態に記録する。
登録の確定は、この確認後の認証済み USB セッションで行う。

### GET /health

受付と DB の準備状態を返す。
この API は、キー、ベッド一覧、観測、姿勢判定を返さない。
準備済みは `200`、保存系が利用不能なら `503` とする。
Jev の欄は最後の通信状態であり、Jev の常時監視ではない。
Jev の未設定・失敗だけでは受付を停止しない。

## 3. 品質条件と Jev

対象期間は `[window_end-180, window_end)` の UTC 秒とする。
ベッドごとに観測秒をまとめ、1 秒につき最大 1 観測を使用する。
同じ秒に複数の観測がある場合は、最後に保存された観測を使う。

次の全条件を満たす場合だけ Jev を呼び出す。

- 180 区間中、162 区間以上に有効観測がある。
- 先頭と末尾を含め、連続欠測が 5 秒以下である。
- 最新観測が期間末尾から 5 秒以内である。
- 到着時刻と観測時刻の差が 5 秒以内である。
- カメラと深度の取得が両方成功している。
- カメラと深度の観測時刻差が 1 秒以内である。
- 各有効観測の深度に、少なくとも 1 セルの status `5` がある。

顔未検知はデータ不足を意味しない。
不足時は `insufficient_data` と区間数・欠測秒数をログへ記録する。
後続の周期で十分なデータが揃った場合は送信を再開する。
受付と保存、他ベッドの判定は継続する。

Jev のモデルは `jev-1.14.0` に固定する。
質問の版は `sensor-posture-v1` とする。
JSON の state に、生の観測 JSONL、設置情報、計算済み品質情報を渡す。
外部へ送る JSONL から、ベッド ID と起動 ID を除外する。
長文用ヘッダ `TypeSafe-Danger-Zone-Long-Context: true` を付ける。
生成した観測 JSONL は 200,000 bytes までとする。
上限超過時は間引かず、`input_too_large` を記録する。
実際の token 上限は別に実 API で確認する。

Choice は `prone / not_prone / unjudgeable` の 3 択とする。
質問は、期間末尾の胴体と支持面の関係を対象にする。
顔の有無や頭の向きだけで胴体姿勢を推定させない。
confidence が 0.9 未満の場合は、判定不能として扱う。
型、モデル、選択肢、確率の範囲と総和を検証する。
選択結果と最大確率の選択肢が矛盾する応答は拒否する。

全体の通信期限は 30 秒とする。
同じ判定窓の再試行は行わない。
周期は単調増加時計で管理し、過ぎた周期をまとめて実行しない。
未設定・通信失敗・不正応答・古い応答は、非うつ伏せへ変換しない。
判定記録には対象期間、判定時刻、モデル、質問の版、回答を残す。
過去の結果を現在の状態として返す API は追加しない。

## 4. マイコンの管理 API

以下は機器側の管理 API 契約である。
商品向けではエッジアプリが認証して使用し、お客様はエッジのローカル設定画面を操作する。
現在の機器内フォームは試作向けであり、URL・キー・CA の手動設定を商品導入の条件にしない。

HTTPS と HTTP Basic 認証を使用する。
ユーザ名は `admin`、パスワードはデバイス固有の 64 桁の秘密とする。

- `GET /`: 設定フォームと取得・送信状態。
- `GET /health`: Wi-Fi、時刻、カメラ、深度、送信の状態。
- `GET /settings`: SSID、ベッド ID、URL、キー設定済みか否か。
- `POST /settings`: 管理設定を検証して保存する。

POST は同一 Origin と `application/json` を要求する。
本文は 2048 bytes 未満とする。
設定キーは以下だけを受け付ける。

```json
{
  "wifi_ssid": "network",
  "wifi_password": "",
  "bed_id": "bed-01",
  "destination_url": "https://edge.example:8443/v1/measurements",
  "device_key": "",
  "clear_device_key": false
}
```

SSID は 1〜32 bytes とする。
Wi-Fi パスワードは 8〜63 文字の印字可能な ASCII とする。
ベッド ID と URL の空欄は、送信停止を意味する。
URL は HTTPS と正しい host / port、固定の受付パスを要求する。
userinfo、query、fragment、制御文字を含む URL は拒否する。
デバイスキーは 64 桁の小文字 16 進文字列とする。
Wi-Fi パスワードとキーの空欄は保存済みの値を維持する。
`clear_device_key:true` はキーを削除する。
秘密を削除した場合は、新しい送信を停止する。
Wi-Fi 設定は再起動後に反映する。
取得 API は Wi-Fi パスワードとキーを返さない。

保存不正は `400`、認証不正は `401`、Origin 不正は `403` とする。
NVS 保存失敗は `500` とし、実行中設定を変更しない。
`/stream`、ポート 81 のサーバ、`/face_box` は廃止する。

### POST /security/certificate

管理証明書の更新に限定し、既存の HTTPS・管理者認証・Origin 検証を要求する。
本文は `application/json` の `certificate` 文字列だけとし、最大 16KiB とする。
登録済み CA による署名、機器内の公開鍵との対応、同一 SAN、serverAuth 用途、有効期間と現在時刻を検証する。
更新前より有効期限が延長された証明書だけを原子的に保存し、保存成功後に `204` を返す。
不正本文・証明書は `400`、過大本文は `413`、認証不正は `401`、Origin 不正は `403`、保存失敗は `500` とする。
更新後の証明書で新規 TLS 接続できることをアプリが確認する。保存・読出しに失敗した場合は直前の証明書を維持する。
秘密鍵、CA、所有者、送信用キーの更新は受け付けず、USB の認証済み登録手順へ分離する。

## 5. 永続化と初期設定

センサー原文と判定記録はエッジの SQLite にだけ保存する。
保存期間は `retention_seconds` で設定する。
初期値は 21600 秒、許容範囲は 180 秒〜365 日とする。
全ファイル合計の上限は 100,000,000 bytes 固定とする。
DB 本体を約 48MB に制限し、rollback journal の余裕を確保する。
削除済みのページは再利用し、通常運転で VACUUM は実行しない。
期限切れの論理除外は即時に行い、物理削除は 1 秒周期で試行する。
削除失敗をログへ記録する。

マイコンでは、暗号化 `secure_nvs` に管理設定と TLS 情報を保存する。
HMAC キーは事前設定済みの eFuse KEY0 を既定として使用する。
別のブロックを使う場合は `CONFIG_NVS_SEC_HMAC_EFUSE_KEY_ID` を変更する。
商品向けは USB の Security 2 セッション内で、登録世代と取引 ID を含む設定を検証して保存する。
USB フレーム最大 32KiB、復号後の設定最大 16KiB とし、認証前の設定要求を拒否する。
設定・信頼根・資格情報を世代単位で切り替え、接続確認と双方の確定前に完了を返さない。
初期登録コード、通常管理の資格情報、復旧受付を区別する。詳細は [接続設計](CONNECTION.md) に従う。
マイコンの管理 TLS 秘密鍵は機器内で生成し、エッジは署名要求に対して証明書を発行する。
秘密を USB の平文、取得 API、シリアルログへ出さない。

現行試作だけは、32KiB 以下の平文 JSON を USB で受け付け、成功時に `PROVISION_OK` を返す。
この経路は相手の認証や登録受付の制限を備えておらず、商品用ビルドから除去する。
現行コード・試作用ツールの説明は [開発者向け SETUP](SETUP.md#開発者向けの現行試作手順) に残す。

## 6. セットアップツール

エッジアプリのローカル画面に、機器追加、設定変更、登録解除、交換、復旧を提供する。
入力は機器固有コード、Wi-Fi、ベッド ID、設置情報とし、秘密の入力欄は非表示にする。
機器 ID はコード認証後に照合し、USB の検出結果だけで設定先を確定しない。
ツールは登録処理を呼び出し、証明書・機器別キー・送信先を自動設定する。
両者の永続化と確定を確認した場合だけ「接続完了」と表示する。
失敗時は失敗した段階と再試行手順を表示し、認証の省略へ誘導しない。
再実行時は保存済みの登録状態を確認し、未確定取引の再開・取消しと登録済み機器の変更を区別する。
設定と認証処理はアプリ本体と共用し、秘密をブラウザの保存領域や診断出力へ残さない。

## 7. OLED 深度マップ

SSD1306 搭載の 128×64px モノクロ I²C モジュールを追加する。
表示処理は実装・自動検証済みであり、配線・視認性・周期・電源は実機未検証である。
配線とモジュールの条件は [接続手順](SETUP.md#22-oled-ssd1306) に従う。

### 配置と更新

- 画面左上を原点 `(0,0)` とし、左側の `x=0..63, y=0..63` に 64×64px のマップを置く。
- 配列の `[row][col]` を、左上 `(col×8, row×8)` の 8×8px 領域へ対応させる。行は下方向、列は右方向に進む。
- 8×8 ゾーンの全てを表示し、余白や罫線でセルの画素を減らさない。補間・平滑化は行わない。
- ULD の配列順序を維持し、表示だけの回転・反転を加えない。実際の視野との対応は設置時に確認する。
- 1 秒周期で最新の深度を表示する。表示のために再測距せず、取得済みの距離・status・取得時刻を同じスナップショットから読む。
- 右側の `x=64..127` は状態表示に使い、正常時は `DEPTH`、異常時は後述の状態を表示する。

### 疑似グレースケール

SSD1306 の各画素は点灯・消灯の 2 階調であるため、空間ディザリングで見かけの濃淡を作る。
画面全体のコントラスト変更や、フレームごとの点滅による階調表現は使わない。
これは距離を見やすくする表示変換であり、送信する測距値は変更しない。

| 項目 | 表示規則 |
| --- | --- |
| 有効セル | `depth.status=ok`、`target_status=5`、距離が 0〜4000mm |
| 距離と明るさ | 固定範囲 0〜4000mm を使用し、0mm は全点灯、4000mm は全消灯。フレームごとの自動正規化は行わない |
| 階調 | 点灯率 `1 - distance_mm / 4000` を最も近い 1/16 刻みに丸め、0〜16 の 17 階調にする。中間値は点灯率が高い側へ丸める |
| ディザリング | 4×4 Bayer 行列の順序ディザリング。各セルの 8×8px に同じ行列を縦横 2 回ずつ配置し、行列値が階調値未満の画素を点灯する |
| 無効セル | status が `5` 以外、または距離が範囲外の場合は、黒地に 8×8px の対角線 2 本で `×` を描く。0mm や遠距離へ置き換えない |

有効セルの例は、0mm が点灯率 100%、1000mm が 75%、2000mm が 50%、3000mm が 25%、4000mm が 0% となる。
濃淡は白黒画素の密度による疑似表現であり、各画素が中間の明るさを持つわけではない。
SSD1306 の画素構成・I²C の根拠は [Solomon Systech データシート](https://cdn-shop.adafruit.com/datasheets/SSD1306.pdf) の 8.1.5、8.7 を参照する。

### 欠測と表示障害

- 起動後に深度をまだ取得していない場合は、マップを消去し `NO DATA` を表示する。
- 深度の取得エラー時は、以前のマップを消去し `ERROR` を表示する。
- 最後に成功した深度の取得から単調時計で 5 秒を超えた場合は、マップを消去し `STALE` を表示する。NTP の時刻補正を経過時間に使わない。
- フレームは新しいが有効セルが 1 個もない場合は、全セルを `×` にし `NO VALID` を表示する。
- 新しい正常フレームを取得したら、現在のマップと状態へ復帰する。
- OLED の初期化失敗・転送失敗はログへ記録する。I²C 転送は 1 回 100ms 以内とし、失敗から 5 秒以上空けて再初期化する。専用タスクで更新し、取得・送信の共有 mutex を転送中に保持しない。
- 同じ I²C バスの電気的障害で深度も取得できない場合は、既存の深度エラーとして扱い、正常値を補完しない。
