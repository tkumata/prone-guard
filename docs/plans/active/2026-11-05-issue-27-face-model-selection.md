# Issue #27 顔検知モデルの選択と保存

## Status

- Phase: verification
- Approval: approved

## Goal

利用者がマイコンの Web 管理画面から、用途に応じて顔検知モデルを選べるようにする。
選択は電源を切っても保持する。
Issue の「ESP-DL」は、現行の MSR + MNP を指すものとして扱う。
ESPDet-Pico 416 も ESP-DL で実行する。

## Scope

- マイコンの管理画面、設定 API、暗号化 NVS、顔検知処理を対象とする。
- 現行の `human_face_detect` コンポーネントに含まれる 2 種類のモデルを使う。
- 承認後に `REQUIREMENTS.md`、`SPECIFICATIONS.md`、`DESIGN.md` の該当箇所を更新する。

## Non-goals

- エッジの設定画面、観測 JSONL、Jev の判定を変更すること。
- ESPDet-Pico 224 の追加、検知閾値の調整、距離別の精度目標を設定すること。

## Required Behavior

- MUST — 認証済みの利用者は、Web 管理画面で `MSR + MNP (現行)` と `ESPDet-Pico 416` を選択して保存できる。
- MUST — マイコンは選択を暗号化 NVS に保存し、再起動時に復元する。
- MUST — 新規設定とモデル項目のない旧設定では、現行の MSR + MNP を既定値とする。
- MUST — 旧設定の Wi-Fi、送信先、資格情報、左右反転の値を保持する。
- MUST — 既存クライアントが POST でモデル項目を省略した場合、保存済みの選択を維持する。
- MUST — 未知のモデル値、不正な型、重複キーを含むリクエストは `400` で拒否する。
- MUST — NVS 保存失敗は `500` を返し、実行中の設定を維持する。
- MUST — 管理画面は、保存が成功するとマイコンが自動で再起動することを保存前に表示する。
- MUST — 保存ボタンは既存の `POST /settings` で設定の保存と再起動を要求する。
- MUST — マイコンは NVS 保存に成功し、成功応答を送信してから自動で再起動する。
- MUST — 入力の検証や NVS 保存に失敗した場合は、エラーを返して再起動を中止する。
- MUST — 再起動の指定を省略した `POST /settings` は、従来どおり保存だけを行う。
- MUST — マイコンは起動時に選択したモデルだけを初期化する。
- MUST — 両モデルの顔矩形を元のカメラの 320×240 座標系に戻す。ランドマークの有効性は、選択したモデルの出力に従う。
- MUST — 選択したモデルで推論できない場合は、カメラの取得エラーとして扱う。

## Tasks

### Task 1 — Web 管理設定と永続化

- **Objective** — 管理画面で選んだモデルを保存し、自動で再起動する。
- **Scope** — 既存の `GET /settings` と `POST /settings` にモデル項目を追加する。POST は保存成功後の再起動を指定できるようにする。管理フォームと NVS の保存・読込みを対応させる。既存の HTTPS、認証、Origin 検証を使う。
- **Acceptance Criteria** — 管理画面でどちらのモデルを保存しても、自動で再起動する。管理画面を再取得すると保存値を表示する。旧形式の両方を読める。不正入力や保存失敗の場合は、設定を維持して再起動を中止する。再起動を指定しない API 呼び出しでは保存だけを行う。
- **Verification** — `sh tests/run.sh` で設定の往復、旧形式、省略、不正入力、保存失敗を確認する。`node tests/test_ui.cjs` でモデルと再起動の指定を送ることを確認する。自動再起動と電源再投入は Task 2 と結合して確認する。

### Task 2 — 保存したモデルで顔検知

- **Objective** — 起動時に Task 1 の設定を読み、選択したモデルで顔検知する。
- **Scope** — 同一のファームウェアに両モデルを含める。MSR + MNP は現行の余白と閾値を維持する。ESPDet-Pico 416 には反時計回りに 90 度補正した 480×640 の画像を渡し、コンポーネントの余白処理と既定の閾値を使う。
- **Acceptance Criteria** — 両モデルに切り替えて推論できる。顔矩形と面積の座標契約、正常な未検知と取得エラーの区別を維持する。ファームウェアが既存のアプリパーティションに収まる。
- **Verification** — `idf.py build` と `idf.py size` でビルドと容量を確認する。顔あり・顔なしの入力で両モデルの座標復元と未検知を確認する。実機の Web 管理画面で両方向に切り替える。保存後の自動再起動と、電源再投入後のモデル選択を起動ログで確認する。実機で推論時間とメモリを測定し、既存の 1 秒送信周期への影響を確認する。

## 検証結果

- `sh tests/run.sh` と `node tests/test_ui.cjs` が成功した。
- ESP-IDF 6.0.3 のビルドとサイズ確認が成功した。アプリは 3,061,296 bytes で、6 MiB のパーティションに収まった。
- ESP32-S3 エミュレーターで両モデルに 11 枚ずつ入力した。顔なし画像は両モデルで未検知になり、検知した顔矩形は 320×240 の範囲に収まった。
- ESPDet-Pico 416 の回転処理の高速化前後で、11 枚の検知結果、スコア、顔矩形が一致した。
- 開発ボードで、モデル項目のない旧設定を MSR + MNP として読み込んだ。
- 最終版の管理 API で不正なモデルを拒否し、再起動指定のない保存では実行中のモデルを維持した。
- 最終版の開発ボードで、`204` 応答後の自動再起動と両方向のモデル切り替えを確認した。再起動後の設定と起動ログを照合した。
- 最終版の USB ログでは、両モデルのカメラ観測と送信試行の間隔の中央値が 1,000 ms だった。エッジへの送信は接続エラーのため未確認。
- ブラウザでの実機操作と物理的な電源再投入は未実施。推論単体の時間とメモリは、計測版の書き込みが自動承認レビューで拒否されたため未測定。
